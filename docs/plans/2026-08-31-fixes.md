## Issue A — `mutation.sh` accepts a package list and ignores it

**Evidence.** Line 16 documents `scripts/mutation.sh [--baseline FILE] [--root DIR] [packages...]`.
The flag loop ends with `*) break ;;` at line 46, leaving the remaining
arguments in `$@`. `$@` is never referenced again: the run loop at lines 90–127
reads only from `$BASELINE`. Positive control on the instrument: `grep -c
BASELINE` returns 7 on the same file, so the grep works and the absence is real.

**Why it matters.** A caller who runs `scripts/mutation.sh ./crash/` asks for
one package and silently gets all five. The gate does something other than what
it was asked, and nothing in the output says so. That is the same family as
`go list -deps` without `-test`: the tool is correct about the work it did, and
the work is not the work requested.

This is not reached by CI, which passes no package argument. It is reached by
any person following the usage text.

### 1. Make the argument work, or remove it from the usage

- [ ] Decide between honouring `[packages...]` as a filter over the baseline
      rows, and deleting it from the usage text.
- [ ] Whichever is chosen, an unknown package name must exit 2 rather than
      silently measuring nothing or everything.

**Acceptance**

- `scripts/mutation.sh ./crash/` either measures `./crash/` alone, or exits 2
  saying the argument is not supported. It must not run all five packages.
- A package name absent from the baseline exits 2.
- `./scripts/mutation-selftest.sh` still passes.
- The selftest gains a row for whichever behaviour is chosen, because a gate
  that cannot report the opposite result is not trustworthy.

## Issue C — no adapter but `fault/sql` proves it invents no failure

**Evidence.** `points_test.go` proves the CORE's zero `Points` never trips. No
adapter proves that it never fails an operation the core did not arm. Counted:
`fs` has two test files using a zero `Points`, `sql` has one, and `alloc`,
`role` and `crash` have none.

The gap is not hypothetical. `sql`'s `rows.Next` held it until this morning:
turning `if r.armed && r.n == r.at` into `if true && r.n == r.at` changed no
test result, and that version fails the first row of EVERY result set, armed or
not.

**The mutation gate does not cover this class for the other adapters.** The
mutant that expresses it rewrites one operand of a compound condition, so it
only exists where the condition is compound. `fs` and `alloc` write
`if f.p.Trip() { ... }`, which has no second operand, so no mutant expresses an
invented failure there and both still sit at a floor of 1.00. A clean mutation
score is not evidence about this property.

**Why it matters more than a missed injection.** A missed injection
under-reports, and the report is still true. An invented one reports a defect
the code under test does not have, so every later finding needs a person to
re-derive whether it is real. `crash/doc.go` already states this about phantom
states, in its own words.

### 3. A zero-`Points` test for each adapter

- [ ] `fs`, `alloc`, `role`, `crash` each get one: drive a representative
      scenario through the adapter with `&fault.Points{}` and assert that every
      operation succeeds.
- [ ] Each carries a positive control in its comment, naming the mutation that
      must make it fail.

**Acceptance**

- Each new test fails when the adapter is made to inject unconditionally, and
  that is demonstrated once per adapter rather than assumed.
- The mutation floors do not move, or the movement is recorded.
- `role`'s version accounts for its per-actor `Points`, which is a different
  zero value from the core's.

## Not an issue, but awaiting a decision

`ResetSession` consumes no operation index. It is the one forwarded operation
that does not count, and it is the opposite of the rule `Begin` follows. The
cause is that the pool decides when to call it, so counting it would make the
N-th operation differ between two runs of one scenario. It is documented in
`sql/doc.go` and held by a test. Reversing it is a small change, and it is the
user's call.
